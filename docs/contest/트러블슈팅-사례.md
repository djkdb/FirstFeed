## 1. 「opus 가 느리다」 → 잠자기였고, 잠자기 감지도 처음엔 틀렸다

- **증상**: 프로필 스냅숏을 만드는 중 `identity_profile → timeout (opus, 4172.9초) — 제한 시간(360초)`, `self_review → timeout (931.4초) — 제한 시간(240초)`
- **내가 본 것** (직접 쓰기):
- **의심 1 (틀림)**: 「opus 가 특정 시간대에 수 분 늦다」 · 한도 — 한도 사용률이 5% 라 버림
- **확인 1**: `pmset -g log` — 그 시각에 `Entering Sleep state due to 'Clamshell Sleep'`(덮개 닫힘). 「느린 시간대」가 잠자기 · DarkWake 반복 구간과 겹쳤다
- **의심 2 (틀림)**: 「단조 시계(hrtime)는 잠든 동안 멈추니 벽시계와의 차이로 잠든 시간을 잰다」 → 그렇게 고쳤는데(`844b11e`), 다음 측정에서 제한 300초 호출이 804초인데도 「잠자기 포함」 표시가 없었다
- **확인 2 (실험)**: 자식 프로세스를 SIGSTOP 8초 → SIGCONT 해 보니 hrtime 도 8,971ms 흘렀다 — **멈추는 것은 프로세스이고 두 시계는 다 흐른다**(그래서 타이머가 깨어난 뒤에 늦게 울린다)
- **고친 것**: 1초 심장 박동 타이머의 벌어진 간격을 잠든 시간으로(`05f2635`). 같은 실험에서 7,971ms 를 잡음. 영향 받은 측정 결과 머리에 정정을 적음(`7bf6176`, 지우지 않음). 측정은 `caffeinate -i` 로 감쌈
- **다시 안 겪게**: 측정 도구를 고치면 **일부러 그 상황을 만들어**(SIGSTOP 등) 확인한다 — 처음엔 「4172초」 한 번의 정황만으로 원인을 확정했다
- 출처: [devlog 2026-10-14-03](../devlog/2026-10-14-03-브랜딩-키트.md) · [2026-10-15-02](../devlog/2026-10-15-02-글-다듬기와-카드-계획.md)

## 2. 새 판을 잰 줄 알았던 측정이 옛 판이었다

- **증상**: 카드 측정(새 판 card_body v3 등)을 근거로 활성 판까지 바꿨는데(`4567c9b`), devlog 를 쓰려고 결과 파일을 다시 읽다가 **머리 줄은 `card_body@v2`** 인데 그 위에 쓴 판정 메모는 「v3 · v4 · v2 반영 판」인 것을 봄
- **내가 본 것** (직접 쓰기):
- **원인**: zsh 에서 `P="--prompt card_body=v3 --prompt …"` 를 따옴표 없이 `$P` 로 넘김 → zsh 는 bash 와 달리 단어로 쪼개지 않아 인자 하나 → 측정 스크립트 다섯 곳에 복사된 파싱이 모양 안 맞는 인자를 **조용히 건너뜀**
- **고친 것**: 파싱을 `scripts/prompt-args.ts` 하나로 모으고, 한 덩어리 인자 · 모양 틀린 값 · 없는 판이면 **시작 전에 멈춤**(같은 `$P` 로 실제로 멈추고 결과 폴더가 안 생기는 것 확인). 10-20 결과에 정정을 적고(지우지 않음) 새 판으로 다시 잼(`2026-10-21-cards-real-v3.md` · `-gen-v3.md`)
- **무엇이 유효했나**: 규칙 A · B 숫자(코드라 프롬프트와 무관), 감상 판정 측정(판을 코드에 고정)은 그대로 유효
- **다시 안 겪게**: 인자는 변수에 담지 않고 그대로 쓴다. 측정 결과를 해석하기 전에 **머리 줄의 판부터** 대조한다
- 출처: [devlog 2026-10-18-03](../devlog/2026-10-18-03-결정-반영과-미리-만든-결과.md)

## 3. 오류 하나 없이 9시간 — 테스트가 틀린 짐작을 굳혔다

- **증상**: 겉으로는 아무 오류도 없었다. 그런데 앱이 Metricool 의 모든 게시물 시각을 9시간 앞당겨 읽어 「게시 48시간 뒤부터」 판정과 「올렸어요 ±3일」 잇기 범위가 틀어짐
- **내가 본 것** (직접 쓰기):
- **처음 짐작**: 「브랜드 시간대가 Asia/Seoul 이니 시각도 KST 겠지」 — 그리고 테스트가 그 값을 기대값으로 적었다
- **의심 1 (판정 안 됨)**: 시간 창으로 잘라 보면 알 수 있다 → 9:10~9:40 과 18:10~18:40(KST) 두 창 모두 같은 게시물이 나왔다. 대신 **Metricool 의 from/to 는 날짜 단위로만 거른다**는 것을 알게 됨
- **확인 (다른 출처와 대조)**: 인스타 게시물 ID 앞부분에는 만든 시각이 들어 있다(`(id >> 23) + 1314220021721` ms). 피드 3개는 Metricool 시각을 **UTC 로 읽었을 때 초까지 같았고**, 릴스 7개는 몇 초~6분 늦었을 뿐(올림 → 게시). KST 로 읽으면 늘 9시간이 어긋났다
- **고친 것**: UTC 로 읽고(`parseStamp`), 테스트를 실제 응답 모양(그 게시물 ID 의 시각 · JSON null · "0")으로 다시 씀
- **다시 안 겪게**: 바깥 서비스를 붙이면 **실제 응답 한 번을 받아 그 모양으로 테스트를 쓴다**. 시각 · 단위처럼 겉으로 안 드러나는 값은 다른 출처와 대조한다
- 출처: [devlog 2026-11-24-01](../devlog/2026-11-24-01-성과-분석-디버깅.md)

## 4. 셸 환경 변수 하나가 과금 경로를 바꾼다

- **증상(실험으로 재현)**: 셸에 `ANTHROPIC_API_KEY` 등이 있으면 `claude` 가 구독 대신 그것을 쓴다
- **내가 본 것** (직접 쓰기):
- **확인한 방법**: 빈 임시 폴더 · `--safe-mode --strict-mcp-config --no-session-persistence --tools "" --model sonnet` 으로, 넣은 값은 모두 **가짜**

  | 환경 | `claude auth status` 의 authMethod | `claude -p` 결과 |
  |---|---|---|
  | 아무것도 없음 | `claude.ai` (구독) | 정상 |
  | 가짜 `ANTHROPIC_API_KEY` | `api_key` (구독 표시 사라짐) | 401 「Invalid API key」 |
  | 가짜 `ANTHROPIC_AUTH_TOKEN` | `oauth_token` | 401 「Invalid bearer token」 |
  | 닿지 않는 `ANTHROPIC_BASE_URL` | — | 60초 동안 응답 없음 |

- **고친 것**: `claude` 를 부를 때(실행 · 로그인 확인 모두) 세 변수를 뺀 환경을 넘긴다. 서버를 가짜 키와 함께 띄우고(`ps eww` 로 서버 환경에 키가 있음을 확인) 시험 호출이 401 없이 통과하는 것을 확인
- **결정**: 셸 환경은 사용자가 앱과 무관하게 바꾸는 것이라, 앱의 과금 경로가 거기에 좌우되면 안 된다
- **다시 안 겪게**: 새 공급자를 붙일 때 「어떤 환경 변수가 과금 경로를 바꾸는가」부터 확인한다
- 출처: [devlog 2026-10-13-03](../devlog/2026-10-13-03-구독-경로-환경-변수와-정정.md)

## 5. 515개 중 1개 — 같은 SQL 이 SQLite 판에 따라 다르게 돌았다

- **증상**: 과제 보고서를 쓰며 단위 테스트를 돌리자 515개 중 1개 실패 — `migrate-004.test.ts`: `TypeError: pillars[0].evidence.map is not a function`
- **내가 본 것** (직접 쓰기):
- **확인한 방법**: 따로 재현 — `SELECT json_set('{}','$.e',(SELECT json_group_array(value) FROM json_each('[1,2]')))` → `{"e":"[1,2]"}`(문자열). 하위 질의를 `json(…)` 으로 감싸면 `{"e":[1,2]}`(배열). 같은 테스트가 SQLite 3.54.1 에서는 실패, 3.53.x 에서는 통과
- **원인**: 함수가 돌려준 JSON 은 바로 바깥 함수에 넘길 때만 JSON 으로 다뤄지고, 하위 질의를 한 번 거치면 보통 글자가 된다
- **고친 것**: 004 는 이미 적용된 파일이라 **고치지 않고**(체크섬 검사에 걸려 서버가 멈춘다) `024_repair_pillar_evidence.sql` 로 문자열 근거만 골라 배열로 되돌림. 테스트 4개(문자열 → 배열 · 배열은 글자 그대로 · 섞인 판 · 두 번 돌려도 같음). 운영자 맥의 실제 DB 는 6개 프로필 중 해당 0개
- **다시 안 겪게**: SQL 안에서 JSON 을 조립할 때 하위 질의 결과는 `json(…)` 으로 감싼다. 변환 마이그레이션 테스트는 `JSON.parse` 한 뒤 **배열인지까지** 본다
- 출처: [devlog 2026-11-27-01](../devlog/2026-11-27-01-근거-문자열-되돌리기.md)
