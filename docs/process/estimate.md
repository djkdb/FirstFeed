> **추정이다.** 아래 「근거」의 실적은 기록에서 잰 것이고, 크기·세션 수는 그 실적에 비춘 판단이다

## 방법

1. 대상마다 **이미 끝낸 FR 중 가장 비슷한 것**을 고른다. 비교 항목: 화면 수 · 새 테이블(마이그레이션) · AI 프롬프트 수(생성 + 평가 기준) · 외부 연동 여부
2. 짝의 **실제 세션 수·커밋 수**(metrics.md 세션 표)를 기준으로 상대 크기 **S(짝의 절반 이하) / M(짝과 비슷) / L(짝보다 큼)** 를 매기고 필요한 세션 수를 범위로 적는다
3. 세션 하나는 지금까지 평균 커밋 13개 · 커밋 기준 약 41분(대화 기준 약 70분) 분량이었다

## 합계를 어떻게 읽을지

- 위 합계는 「짝의 실적」만 비춘 **기본 범위**다. 지금까지 13세션 중 **6세션은 FR 을 끝내지 않은 다듬기·측정·결정 반영 세션**이었다(metrics.md). 짝의 실적에 일부 다듬기가 들어 있긴 하지만(카드뉴스 3세션 등), 같은 비율로 더 들 수 있다고 보면 **13~23세션**까지 잡아 두는 것이 안전하다
- 세션당 커밋 기준 41분 · 대화 기준 약 70분으로 치면 기본 범위는 대화 기준 **약 12~18시간**, 넓게 잡으면 **약 15~27시간**
- 순서 제약: FR-IN-5 → IN-6 은 IN-2·IN-4 가 먼저, FR-OP-4 → OP-5 는 OP-1·OP-2 가 먼저(같은 할 일 표를 쓴다)

## 불확실한 점 (따로)

1. **캡처 이미지 읽기를 제품에서 한 번도 안 써 봤다** — 어댑터·공급자에 이미지 입력 길은 있지만(`claude-code.ts` 의 images), 실제 AI 로 쓴 기능은 없고 테스트만 있다. FR-IN-2·FR-OP-2 ② 가 여기에 기대서 L 로 잡았고, 정확도가 낮으면 더 커진다
2. **FR-IN-2 의 「읽은 숫자 옆에 원본 캡처 구역」** — 숫자마다 캡처 속 위치가 필요하다. AI 가 위치(좌표)를 믿을 만하게 주는지 확인 못 함. 안 되면 사용자가 구역을 고르는 화면이 따로 필요
3. **FR-OP-2 ③ 이메일 연동은 FR-OP-3(Gmail OAuth)에 달렸다** — 이번 대상 목록에 OP-3 이 없다. ③ 없이는 OP-2 수용 기준(세 경로 모두)을 다 채울 수 없다. 외부 승인이 필요해 기간도 우리 쪽에서 정할 수 없다
4. **FR-IN-6 의 「발굴 추천에 반영」은 FR-DS(발굴 탭)가 없으면 확인할 곳이 없다** — 지금 FR-DS 는 모두 안 함. 제목 생성 반영만으로 끝낼지 결정이 필요
5. **FR-IN-4 의 「제목 유형」 분류 방법이 정해지지 않았다** — 코드 규칙(질문형·숫자형 등)이면 S, AI 분류면 프롬프트 + 평가가 더 든다
6. **실적 자체의 불확실성** — 세션은 devlog 단위라 길이가 들쭉날쭉하고(커밋 기준 1~107분), 작업 시간은 커밋·대화 두 방법이 1.7배 차이 난다. 같은 사람·같은 도구(Claude Code)라는 조건이 바뀌면 이 숫자도 바뀐다
7. **측정에 드는 시간** — 지금까지 AI 출력이 있는 기능은 모두 「측정 → 프롬프트 v2 → 다시 측정」을 거쳤다(정체성·브랜딩·카드). AI 를 쓰는 대상(MK-3·MK-7·IN-2·IN-5·OP-2·OP-4)도 같은 과정을 거치면 세션이 늘어난다. 위 범위의 위쪽 끝이 이 경우다
